5-Stage Pipelined RISC-V CPU in Verilog

2026

I designed and implemented a complete 5-stage pipelined CPU in Verilog that executes the RISC-V RV32I instruction set. The project covers the full design from individual logic components up to a working processor, including all the hazard mitigation techniques a real pipeline requires: data forwarding, load-use stalling, and control flow flushing. I also built a single-cycle reference implementation for comparison, a comprehensive test suite, and a Python-based build system.

The complete source is available on GitHub.

Why pipelining?

A single-cycle CPU completes one instruction per clock cycle but must run the clock slowly enough for the slowest instruction to finish. Pipelining overlaps the execution of multiple instructions: while one instruction is in the execute stage, the next is being decoded, and the one after that is being fetched. This allows the clock to run much faster, improving throughput significantly.

The pipeline I implemented has five stages: Instruction Fetch (IF), Instruction Decode (ID), Execute (EX), Memory (M), and Write Back (WB). Each stage operates on a different instruction every cycle, with intermediate pipeline registers holding state between stages.

Cycle:      1    2    3    4    5    6    7
Instr 1:    IF   ID   EX   M    WB
Instr 2:         IF   ID   EX   M    WB
Instr 3:              IF   ID   EX   M    WB
Instr 4:                   IF   ID   EX   M    WB

Architecture Overview

The CPU uses a Harvard-style architecture with separate instruction memory and data memory, which allows an instruction fetch and a data load/store to happen in the same cycle. The design is broken into 25 individual Verilog modules that each handle a specific task:

  • ALU — 32 arithmetic and logic operations (add, sub, AND, OR, XOR, shifts, set-less-than)
  • Control unit — decodes each instruction and produces 18-bit control signals
  • Immediate generator — extracts and sign-extends I, S, B, U, and J format immediates
  • Register file — 32 × 32-bit registers with two read ports and one write port
  • Instruction memory / Data memory — separate memories; dmem supports byte, half-word, and word accesses
  • Pipeline registers (IF/ID, ID/EX, EX/M, M/WB) — hold state across stage boundaries
  • Hazard mitigation units — forwarding, stalling, and flushing (described below)

The Hazard Problem

Pipelining introduces hazards: situations where the correct result of one instruction is not yet available when a later instruction needs it. Without mitigation, a pipeline would produce silently wrong results. There are three classes of hazard I had to solve:

1. Data Hazards — Forwarding

When instruction A produces a value and instruction B immediately uses it, B reaches the Execute stage before A's result has been written back to the register file. The solution is data forwarding (also called operand bypassing): route the result directly from wherever it currently sits in the pipeline to the point where it is needed, bypassing the register file entirely.

I implemented three forwarding paths:

Path Source → Destination Latency
MX Forward M stage result → EX stage ALU input 0 cycles
WX Forward WB stage result → EX stage ALU input 0 cycles
WM Forward WB stage result → M stage store data 0 cycles

The forwarding unit compares the destination register of instructions in the M and WB stages against the source registers of the instruction currently in EX. When a match is found, multiplexers in the EX stage select the forwarded value instead of the stale register file output. MX forwarding is checked first; if both M and WB are writing to the same destination, M takes priority.

With forwarding, a sequence of back-to-back ALU instructions executes with zero stall cycles:

add x1, x0, x0    # result available in M by cycle 4
add x2, x1, x0    # x1 forwarded from M  → no stall
add x3, x2, x0    # x2 forwarded from WB → no stall

2. Load-Use Hazards — Stalling

Forwarding cannot handle every case. A load instruction (lw, lh, lb) retrieves its result from data memory at the end of the M stage. If the very next instruction needs that value, it will be in the EX stage while the load is still in M — one cycle too early for MX forwarding to work.

The stalling unit detects this condition and inserts a one-cycle bubble: the PC and IF/ID register are frozen for one cycle, and a NOP is injected into the ID/EX register. After the stall, the load result is in the M stage and MX forwarding takes over.

Cycle:    1     2     3       4          5
lw x1:   IF    ID    EX   →  M (stall)  WB
add x3:        IF    ID   →  ID (stall) EX ← x1 forwarded from M

3. Control Hazards — Flushing

Branch and jump decisions are resolved in the EX stage (cycle 3 of an instruction). By that point, two instructions have already been fetched and partially executed down the wrong path. When a branch is taken, those instructions must be invalidated.

The flush unit monitors the EX stage and, when a branch is taken or an unconditional jump is executed, replaces the IF/ID register contents with a NOP and redirects the PC to the branch target. This costs one incorrectly-fetched instruction per taken branch.

I handled JAL specially: since JAL's target is PC-relative and fully computable at fetch time, I resolve it in the IF stage with zero penalty. JALR requires reading a register, so it resolves in ID with a one-cycle penalty.

Hazard Mitigation Penalty
ALU-to-ALU dependency MX or WX forwarding 0 cycles
Load followed by use 1-cycle stall + MX forward +1 cycle
Branch not taken Static not-taken prediction 0 cycles
Branch taken Flush IF/ID, redirect PC +2 cycles
JAL (unconditional jump) Resolved in IF stage 0 cycles
JALR (register-indirect jump) Resolved in ID stage +1 cycle

Instruction Set Coverage

The CPU implements the RISC-V RV32I base integer instruction set. I tested 37 out of the approximately 40 core instructions, covering all six instruction encoding formats:

  • R-type — add, sub, and, or, xor, sll, srl, sra, slt, sltu
  • I-type — addi, andi, ori, xori, slli, srli, slti, lw, lh, lb, jalr
  • S-type — sw, sh, sb
  • B-type — beq, bne, blt, bge, bltu, bgeu
  • U-type — lui, auipc
  • J-type — jal

Testing Methodology

I wrote 42 testbenches in total: 19 unit tests targeting individual components and 23 integration tests that run real RISC-V assembly programs through the full CPU pipeline.

Each integration test assembles a program using the RISC-V GNU toolchain, converts it to a Verilog hex file, and loads it into the simulated instruction memory. After execution, the testbench reads the register file and data memory and compares them against expected values. Tests also generate VCD waveform files for analysis in GTKWave when I needed to step through a hazard scenario signal by signal.

The test suite includes dedicated hazard tests designed to exercise each mitigation path in isolation:

  • load_use_hazard — specifically triggers the stalling path
  • branch_cmp — exercises all six branch conditions and the flush mechanism
  • jal_fwd_hazard — tests JAL with forwarding-dependent operands
  • store_load — exercises the WM forwarding path from WB to the M stage store port

I automated everything through a set of Python scripts. Running all 102 tests (across both the pipelined and single-cycle implementations) and saving timestamped results takes a single command. All 102 tests pass.

What I learned

Building a pipeline from scratch forced me to think carefully about timing in a way that single-cycle and behavioral-level designs do not. Forwarding in particular required tracing every data path through the pipeline and deciding, for every possible pair of consecutive instructions, whether a hazard exists and which mux select line resolves it. Getting the forwarding priority logic right — MX before WX when both match — took several iterations of testbench-driven debugging.

The experience also gave me a concrete feel for the tradeoffs real architects make: static branch prediction is simple to implement but burns cycles on every taken branch; a branch predictor would recover those cycles at the cost of significantly more hardware and design complexity. Designing within those tradeoffs, rather than just reading about them, is what made this project valuable.
