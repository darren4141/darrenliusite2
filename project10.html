Bare-Metal RTOS for Raspberry Pi CM4

2026

I built a preemptive real-time operating system from scratch in C and ARM assembly, running on a Raspberry Pi Compute Module 4 (BCM2711, Cortex-A72). The OS runs entirely bare-metal and uses a priority-based preemptive scheduler, IRQ-driven context switching, hardware drivers, and synchronization primitives.

Startup Sequence

The default RPi GPU firmware hands control to the reset handler at 0x8000 in HYP mode.

Memory Layout

The boot chain is actually three separate images now, not two — a minimal bootstrap that lives on the SD card, a self-updatable bootloader on eMMC, and the RTOS application itself — each linked at its own fixed address so loading the next stage never overwrites the one currently executing. The bootstrap (0x8000) is what the GPU firmware loads; it brings up just enough (UART + eMMC) to CRC-validate and load the bootloader at 0x10000. The bootloader is the real policy layer: it validates the app's CRC (or trusts the preserved boot flags on a DFU-triggered warm reset), opens a short DFU recovery window, and loads the app at 0x88400. A 4 KB shared-flags region at 0x88000 survives watchdog resets — it carries the BootFlags struct (magic, reset reason, DFU-requested flag, CRC-valid flag) and, at 0x88300, the mailbox address a companion core's entry point gets written to before it's released (see the Companion Core box in the system map above). The app itself now lives in one of two A/B slots on eMMC, so a bad flash can be rolled back without bricking the board.

The Scheduler

The scheduler uses six separate ready lists, one per priority level, and a single sorted delay list for blocked tasks. All list operations use an intrusive doubly-linked list: each Task Control Block (TCB) contains two embedded ListItem structs, one for the ready/blocked list and one for future event synchronization. This avoids any dynamic allocation inside the scheduler itself and keeps insertion and removal O(1).

Scheduler Data Structures
─────────────────────────────────────────────────────────────

ready_list[PRIORITY_5]  ←── head ↔ TCB ↔ TCB ↔ TCB  (highest priority)
ready_list[PRIORITY_4]  ←── head ↔ TCB
ready_list[PRIORITY_3]  ←── head ↔ TCB ↔ TCB
ready_list[PRIORITY_2]  ←── head (UART task lives here)
ready_list[PRIORITY_1]  ←── head
ready_list[PRIORITY_0]  ←── head (lowest priority)

blocked_task_list       ←── sorted by wakeup_time ascending
                              head ↔ TCB[t=105] ↔ TCB[t=200] ↔ TCB[t=500]

On every 1 ms tick the scheduler scans from PRIORITY_5 down to PRIORITY_0 and picks the index task from the highest non-empty ready list. If multiple tasks share the same priority, a round-robin index advances one step each tick, giving each equal CPU time. The currently running task is marked RUNNING; all others in the ready lists are marked READY.

Task Lifecycle

A task is created with task_create(), which allocates a TCB and a stack from the 16 KB static heap, initializes the stack to look like a task that was interrupted mid-execution (so the context-restore code in the IRQ handler works correctly from the very first switch), and inserts it into the appropriate ready list. From there a task cycles between READY, RUNNING, and BLOCKED states driven by the tick interrupt.

Context Switching

Context switching happens inside the IRQ handler, which fires every 1 ms from the ARM Generic Timer. The ARM hardware does not automatically save registers on an IRQ — that is entirely my responsibility. The handler saves the interrupted task's full register set (r0–r12, LR, SPSR) to that task's SVC-mode stack, calls the scheduler to pick the next task, then restores from the new task's stack and returns.

IRQ Handler — Register Save / Restore
──────────────────────────────────────────────────────────
IRQ fires (CPU auto-saves nothing in AArch32 IRQ mode)
     │
     ▼
sub  lr, lr, #4            // adjust LR_irq to point to interrupted instruction
srsdb sp!, #0x13           // push {LR_irq, SPSR_irq} to SVC stack (mode 0x13)
cps  #0x13                 // switch to SVC mode (now on task's stack)
push {r0-r12}              // save general-purpose registers

     Current task's SVC stack (grows downward):
     ┌──────────────┐  ← SP before IRQ
     │   r0         │
     │   r1         │
     │   ...        │
     │   r12        │
     │   LR_irq     │  (return address)
     │   SPSR_irq   │  (interrupted task's CPSR)
     └──────────────┘  ← task's p_TopOfStack saved here
            │
            ▼
     Call timer_tick_handler()    // advance timer, unblock tasks
     Call schedulerSwitchContext() // pick next task, update p_task_control_block

     Load new task's SP from TCB
            │
            ▼
     pop  {r0-r12}              // restore general-purpose registers
     rfeia sp!                  // atomic: pop PC and CPSR, return to task
                                // (also re-enables IRQs via CPSR.I)

The key instruction is rfeia sp! — Return From Exception, Increment After. It atomically pops the saved PC and SPSR into the PC and CPSR in a single instruction, making the context switch race-free without needing to explicitly re-enable interrupts.

Timer and Tick Source

The 1 ms tick comes from the ARM Generic Timer's CNTP (non-secure physical timer), which is separate from the BCM peripheral timer and runs at a fixed 54 MHz regardless of CPU clock scaling. On each tick the handler reads the current compare value (CNTP_CVAL), adds exactly 54,000 counts (54 MHz / 1000 Hz) and writes it back — this prevents tick drift from accumulating over time because the next deadline is always relative to the previous one, not to when the handler actually ran.

ARM Generic Timer — 1 kHz Tick
──────────────────────────────────────────────────────────
CNTFRQ = 54,000,000 Hz
tick_period = 54,000,000 / 1,000 = 54,000 counts

Timer fires when CNTPCT >= CNTP_CVAL

                                        │◄────────────────►│
───────────────────────────────────────────────────────────────►
                         ▲                                 ▲
                   IRQ fires here               CNTP_CVAL += 54000
                   (tick_count++)                  (next deadline)

In gentimer handler:
  CNTP_CVAL = CNTP_CVAL + 54000   ← always relative to last deadline,
                                     never relative to "now"

Task Stack Initialization

When a task is first created, it has never run, so there is no saved context to restore. I pre-initialize each task's stack to look exactly like the IRQ handler just saved it — with the task function address as the saved PC, the task parameters in r0, and a CPSR value that puts the CPU in SVC mode with interrupts enabled. The first context switch into that task is then identical to restoring any other task's context.

Initial task stack layout (grows downward, set by task_create):
                                           ← p_TopOfStack
┌─────────────────────────────────────┐
│  SPSR = 0x00000013 (SVC, IRQ on)   │  ← will become CPSR on first run
│  PC   = &task_function              │  ← task entry point
│  r12  = 0x00000000                  │
│  r11  = 0x00000000                  │
│  ...                                │
│  r1   = 0x00000000                  │
│  r0   = params pointer              │  ← first argument to task function
└─────────────────────────────────────┘

When rfeia restores this stack for the first time:
  CPU enters SVC mode, IRQs enabled, jumps to task_function(params)
  — identical to restoring a preempted task

Interrupt Routing

The GIC-400 manages interrupt delivery to the cores. The ARM Generic Timer uses interrupt ID 30 (the non-secure physical timer PPI). I configure the GIC distributor to enable that interrupt, set its priority, and route it to Core 0. One gotcha on the CM4: the physical timer is in GIC security group 1 by default, which means the standard GIC GICD_ISENABLER route can be blocked. I work around this by also writing to the ARM Local timer routing register to force the interrupt to Core 0's IRQ line.

UART Driver

The PL011 UART driver operates in two modes. In full mode (used by the kernel), transmit data goes into a 1024-byte ring buffer, and a dedicated UART task at PRIORITY_2 drains the buffer into the hardware whenever bytes are waiting. This keeps the calling task from blocking on slow UART writes. In minimal mode (used by the bootloader), the driver just spins until the TX FIFO has space — simpler but sufficient for the low-throughput bootloader protocol.

Bootloader and DFU

I also wrote a separate bootloader image (boot7l.img) that loads first and is responsible for validating and jumping to the kernel. On startup it checks the shared boot flags: if a firmware update was requested, it enters DFU mode; otherwise it validates the kernel CRC and jumps to 0x88400. The DFU protocol operates over UART and uses a simple framed packet format with a 32-bit CRC for error detection.

Static Memory Model

The kernel uses no dynamic memory allocation after boot. I wrote a 16 KB bump allocator that is only called during task creation — it advances a pointer forward and never frees anything. Since the number of tasks is fixed at compile time (MAX_NUM_TASKS = 16) and each task's stack depth is specified at creation, the total memory usage is deterministic and there is no risk of heap fragmentation causing a runtime failure.

What I learned

The most technically demanding part was getting the context switch right. The ARM architecture has separate banked registers for each privilege mode, and the srsdb / rfeia instructions are specifically designed for preemptive OS context switching — but using them incorrectly causes hard-to-debug crashes because the CPU silently uses the wrong stack pointer. I spent a significant amount of time working through which stack was active at each point in the IRQ handler, cross-referencing the ARM architecture reference manual.

A close second was the initial CM4 bringup. The firmware leaves the CPU in HYP mode with the D-cache enabled, and getting through those two issues (wrong mode for SVC calls, broken MMIO reads) required understanding the SCTLR vs HSCTLR distinction, the CNTHCTL_EL2 register that gates physical timer access, and the GIC security group restrictions. None of this appears in typical embedded tutorials because most people use a BSP that handles it.

Building the entire software stack myself — from the reset vector through the scheduler to the application tasks — gave me a much clearer picture of what an RTOS actually does versus what is provided by hardware. The scheduler is only about 250 lines of C. The context switch is about 30 lines of assembly. It turns out that the core of an RTOS is not especially large; the complexity is in understanding exactly what the hardware does and does not do for you.

Mutex

A priority-inheritance mutex implementation.

How it works

Each Mutex carries its own Spinlock since a waiter can live on a different core than the owner. mutex_lock() is managed by the scheduler systick. If inheritance is enabled and the caller is higher priority than the current owner, the owner's priority is boosted for as long as it holds the mutex.

struct Mutex {
  MutexState         state;               // locked or unlocked
  TaskControlBlock  *mutex_owner;         // task currently holding it
  List               mutex_blocked_list;  // tasks waiting
  uint8_t            inheritance_enabled; // priority inheritance on/off
  TaskPriorityLevel  inherited_priority;  // highest priority among current waiters
  Spinlock           lock;                // cross-core lock on this struct
#ifdef RTOS_TELEMETRY
  uint16_t           sync_id;             // telemetry builds only
#endif
};

Finding the next owner

mutex_unlock() finds the next owner and the second-highest waiting priority in a single pass over the blocked list:

while (iter != NULL) {
  if (iter->owner->priority > best->owner->priority) {
    if (best->owner->priority > second_best) second_best = best->owner->priority;
    best = iter;
  } else {
    if (iter->owner->priority > second_best) second_best = iter->owner->priority;
  }
  iter = iter->next;
}

Semaphore

A counting semaphore for signaling between tasks and interrupt handlers.

Overview

semaphore_take() blocks by adding the task to a FIFO list and blocking until something wakes it - either semaphore_give() or a timeout from the scheduler tick. semaphore_give() hands its count directly to the next waiting task instead of incrementing the counter and letting it race to claim it. give() also locks the waiting task's own core, not the caller's core, so it's safe to call from a task or ISR on one core to wake a task sitting on another core's ready list.

struct Semaphore {
  uint32_t max_count;                // ceiling
  uint32_t count;                    // current value
  List     semaphore_blocked_list;   // FIFO wait list
  Spinlock lock;                     // cross-core lock on this struct
#ifdef RTOS_TELEMETRY
  uint16_t sync_id;                  // telemetry builds only
#endif
};

Semaphore take & give execution

Semaphore take with timeout

semaphore_take() can also be called with a timeout parameter so that the caller is guaranteed to return after a certain amount of time. If the timeout expires without the semaphore being acquired, then semaphore_give() will return E_TIMED_OUT

Queue

A fixed-capacity message queue built on top of two semaphores.

Overview

queue_init() allocates its backing buffer with one heap_malloc() call, then sets up two semaphores: space_available starts at full capacity, data_available starts at 0 — the standard producer/consumer pattern. queue_send()/queue_recv() copy an item in or out byte-by-byte (no libc, no memcpy in this freestanding build) and have no wait-list logic of their own; both blocking paths go through semaphore.

struct Queue {
  uint8_t  *buf;                   // backing buffer, capacity * item_size bytes
  uint32_t  head;                  // write index
  uint32_t  tail;                  // read index
  uint32_t  capacity;              // max number of items in the queue
  uint32_t  item_size;             // bytes per item

  Semaphore space_available;       // gates queue_send
  Semaphore data_available;        // gates queue_recv

  Spinlock  lock;                  // guards the byte-copy step
#ifdef RTOS_TELEMETRY
  uint16_t  sync_id;                // telemetry builds only
#endif
};

Ring buffer operation:

Queue send/receive operations

Sized for any item type

queue_init() takes item_size as a parameter and allocates capacity * item_size bytes for the backing buffer. queue_send()/queue_recv() don't know or care what type is being queued — src and dst are void *, and both copy exactly item_size bytes to or from the buffer at head/tail's offset. The same Queue works for single bytes or large structs; only the numbers passed to queue_init() change.

Software Timer

Tick-driven timers built on top of the scheduler. All software timers live in a software timer handler task. Software timers can be configured to have one-shot or repeating callbacks.

Overview

Each SoftwareTimer sits in one of two lists: a blocked list sorted by expiry_tick, and an active list. software_timer_tick() runs in on the scheduler systick and moves expired timers onto the active list and signals a semaphore. The callback itself runs later, off the tick, on a dedicated sw_timer service task. Periodic timers re-arm relative to their scheduled expiry (expiry_tick += period), not to when they actually ran, to prevent drift.

struct SoftwareTimer {
  uint64_t       expiry_tick;   // scheduler tick this timer next fires at
  uint64_t       period;        // ticks between fires (periodic) or until fire (one-shot)

  TimerMode      timer_mode;    // one-shot or periodic
  TimerCallback  callback;      // runs when it fires

  TimerListId    list_id;       // which list this node is currently in
  SoftwareTimer *next;          // intrusive singly-linked list link
};

UART

UART driver with RX calls that automatically switch between blocking and task-based transmission.

Overview

uart_tx() operations all check uart_task_started before every write. Until a channel's TX task has been started, they fall through to raw blocking implementation, which happens during early boot, before the scheduler or task exists. Once uart_channel_task_start() has been called for a channel, the same calls instead enqueue into a ring buffer and wake a dedicated uart_tx_task with a semaphore. The UART buffer + task mechanism is guarded by a spinlock and can be accessed from any core

UART buffer + task mechanism

The UART buffer and task mechanism keeps uart calls lightweight which is important for an RTOS. Additionally, it prevents jumbled/stomped UART messages when multiple cores & tasks try to write through the same UART peripheral.

kmain()
  uart_channel_init(...)
  uart_print("booting...")       -> raw PIO, straight out
  scheduler_init(...)
  uart_channel_task_start(...)   -> creates uart_tx_task
  scheduler_start()
  ...
  uart_print("running")          -> same call, now enqueues
                                     + wakes uart_tx_task

How _irq_handler dispatches

The assembly IRQ handler in startup.s checks the interrupt ID and routes it to the appropriate IRQ.

_irq_handler (startup.s), after saving r0-r12 to the task's own SVC stack:

read this core's Core0 IRQ Source register (ARM Local)
  bit 4 (mailbox 0) set?
    yes -> mailbox_park_request$   (companion-core IPI —
                                     GICC_IAR/EOIR never touched)
    no  -> read GICC_IAR  (acknowledges + returns the pending INTID)
             ID == 0x3FF ?  -> spurious, done
             ID == 30 ?     -> cntx_switch$ — inline-asm context switch;
                                calls timer_tick_handler() and
                                scheduler_switch_context() in C, but the
                                actual SP save/restore stays in assembly
             else           -> cps to IRQ mode, bl irq_dispatch(intid)
                                (the C table gic_enable_spi() callers
                                 register into via irq_register())

                        both of the last two cases fall through to:
                        write GICC_EOIR with the saved IAR value

Interrupts

A flat, 256-entry INTID→handler table.

Overview

irq_register() populates g_handlers[intid]; it never touches the GIC itself — enabling the interrupt at the GIC (or ARM Local controller) is a separate call the registering code makes on its own. irq_dispatch(intid) is what the assembly _irq_handler calls after reading either GICC_IAR or the ARM Local Core0 IRQ Source register, depending on which path fired.

irq_dispatch() reads the table with no lock: a word-aligned pointer load is atomic on ARMv8, so there's nothing to race on the read side. irq_register() does take a critical section around its write, since a registration could otherwise race that read. It's intentionally the thinnest possible layer between the vector table and C handlers.

Watchdog

A free-running PM watchdog with A/B app-slot rollback.

Overview

watchdog_init() arms the BCM2711 PM watchdog (timeout clamped to 1–15s) from a caller-owned WatchdogConfig; watchdog_task_start() kicks it every 2 seconds and, if configured, arms a confirm-slot timer that clears the current app's "on trial" flag once it's run long enough to be trusted. wdt_meta (persisted to eMMC, CRC-checked) tracks reset count, active slot, and trial state across reboots.

Because the kick lives on a task, it's tied to the scheduler running at all: halting the CPU with a JTAG debugger freezes every task including the one that kicks every 2 seconds, and the watchdog will fire a full SoC reset (resetting the debug logic mid-session too) if the configured timeout elapses while halted:

JTAG halt (breakpoint/pause)
   │
   ▼
scheduler frozen ──► watchdog_task can't kick ──► timeout elapses
   │                                                       │
   ▼                                                       ▼
CoreSight/debug logic ◄──────── full SoC reset ◄───────────┘
also reset mid-session

Fix: comment out watchdog_init()/watchdog_task_start() before a JTAG
session, unless you're specifically testing watchdog behavior.

Separately: tolerance=0 in WatchdogConfig is not "never roll back" — the bootloader check is wdt_reset_count > tolerance, so a tolerance of 0 trips the reset policy on the very first watchdog reset. Only a negative tolerance (WATCHDOG_RESET_TOLERANCE_INFINITE) actually disables it.

Scheduler

A 6-level priority, round-robin scheduler — one fully independent instance per core.

Overview

See the Startup, Scheduler, and Context Switching sections earlier on this page for the full walkthrough of ready lists, the blocked list, and the IRQ-driven context switch. The short version: each core owns its own scheduler_init() call, its own ready/blocked lists, its own idle task, and its own Spinlock — a task's core_id never changes once created; there's no task migration.

typedef struct {
  List               ready_list[NUM_TASK_PRIORITIES]; // one per priority level
  List               blocked_task_list;               // sorted by wakeup_time
  volatile uint32_t *s_clk_freq;                       // this core's timer frequency
  volatile uint64_t *s_tick_count;                     // this core's tick counter
  uint32_t           hz;                               // tick rate (1000)
  Spinlock           lock;                             // this core's scheduler lock
  TaskControlBlock   idle_tcb;                         // this core's idle task
  StackType_t        idle_stack[IDLE_STACK_DEPTH];     // idle task's stack (64 words)
} SchedulerCore;

static SchedulerCore g_cores[COMPANION_CORE_MAX_CORES];  // one per core, indexed by core_id

"Blocking" in this kernel is a busy-wait, not a true block — mutex_lock(), semaphore_take(), and task_delay_ms() all spin on the task's own current_state field, on its own stack; the only thing that ever flips that state is the 1 kHz timer ISR or another task's explicit wake call. The stack-watermark check inside scheduler_switch_context() is deliberately fatal rather than recoverable: if a task's watermark byte doesn't match on a context switch, the scheduler spins forever right there instead of trying to continue, so a JTAG session can inspect task_id and stack_base at the exact instant of the overflow.

Mutex and semaphore both carry their own lock separate from any core's scheduler lock (see those pages), and there's a strict ordering rule for code that holds both:

Correct order (what mutex_lock()/semaphore_take() do):
  1. acquire the Semaphore's/Mutex's own lock
  2. acquire scheduler_lock(core_id)          <- inner

If a call site ever reversed that order:
  Core 0: holds scheduler_lock(0), waits for mtx.lock
  Core 1: holds mtx.lock,          waits for scheduler_lock(0)
  -> neither can proceed

Tasks

task_create() — the one function that turns a plain C function into a schedulable unit of execution.

Overview

task_create() allocates a TaskControlBlock from a fixed per-core pool (16 slots per core, MAX_NUM_TASKS) and a stack from the kernel heap, fills the stack with a watermark byte, hand-builds a fake initial exception frame, and adds the task straight onto its core's ready list. task_types.h — the header defining TaskControlBlock, the intrusive List/ListItem types, priority levels, and task states — has no .c file of its own; it's the shared vocabulary task.c and scheduler.c both operate on, which is why this page treats "Tasks" as one component covering both.

struct TaskControlBlock {
  volatile StackType_t *current_sp;  // live SP, saved/restored on every switch
  StackType_t          *stack_high;  // top of allocated stack (initial SP)
  StackType_t          *stack_base;  // bottom of stack; watermark check
  uint16_t              stack_depth;

  uint16_t              task_id;
  uint32_t              core_id;     // which core's scheduler owns this task

  volatile TaskState    current_state;
  TaskPriorityLevel      priority;
  uint64_t               wakeup_time;

  ListItem               state_list_item;  // ready/blocked list node
  ListItem               event_list_item;  // mutex/semaphore wait node

  volatile TaskWakeupReason wakeup_reason;

  TaskPriorityLevel      base_priority;    // pre-boost priority
  uint32_t               mutexes_held;     // inheritance-enabled mutexes held
};

task_init_stack() builds a task's very first stack frame to look exactly like a context switch already happened to it:

stack_high  ┌───────────────────────────┐
            │ SPSR = 0x00000013         │  SVC mode, IRQs enabled
            ├───────────────────────────┤
            │ PC   = task_function      │  entry point
            ├───────────────────────────┤
            │ LR   = task_exit_trap     │  catches a task that returns
            ├───────────────────────────┤

Heap

A 256 KB bump allocator — the entire dynamic memory story for this kernel.

Overview

static uint8_t   heap[HEAP_SIZE_BYTES];   // 256 KB, HEAP_SIZE_BYTES = 262144
static uint32_t  heap_offset = 0;
static Spinlock  heap_lock;               // guards heap_offset across cores

void *heap_malloc(uint32_t size)
{
  size = (size + 3) & ~0b11;              // round up to 4-byte alignment

  if (heap_offset + size > HEAP_SIZE_BYTES) {
    return NULL;
  }
  void *block_start = &heap[heap_offset];
  heap_offset += size;
  return block_start;
}

No free-list, no fragmentation handling, no free() at all — every allocation happens at boot (task stacks, TCBs, fixed buffers) and lives for the life of the program, so there's nothing to reclaim. Callers like task_create() and queue_init() check the NULL return explicitly.

Companion Core

Releases cores 1–3 from their boot-time parking loop into independent RTOS instances — and recovers them across a software reboot without a power cycle.

Overview

companion_core_start(core_id, entry) hands a secondary core a bare function pointer over a fixed cross-image mailbox address and wakes it with an SEV; companion_core_id() reads the calling core's own id straight off MPIDR. This module itself is AMP, not SMP — there's no shared ready list or task migration here. What a released core actually does with that entry point is run its own complete, independent scheduler_init()/task_create()/scheduler_start() sequence: a second full instance of everything in the Base of RTOS / Kernel tier above, on its own core.

typedef struct {
  volatile uint32_t expected_mask;          // which cores should report in
  volatile uint8_t  core_kicked[COMPANION_CORE_MAX_CORES]; // per-core kick flags
} CompanionCoreContext;

Shared bookkeeping, owned by the caller and linked in via companion_core_init() — expected_mask gets a bit set for every core released through companion_core_start(), and Watchdog's multicore mode uses core_kicked to track which of those cores has reported in (see the Watchdog page).

Core 0 (conductor)                    Core 1 (companion)
   │  write entry fn ptr                    │
   │──────► mailbox[1] ────────────────────►│  parked, waiting on SEV
   │  sev                                   │
   │                                        ▼
   │                              runs own scheduler_init()
   │                              /task_create()/scheduler_start()
   │                              — a second full kernel instance
   │
   ── DFU soft reset (core 0 only — a jump, not a hardware reset) ──
   │
   │  companion_core_reset_active()
   │──────► ARM Local mailbox 0 IPI ────────►│  (not a GIC SGI — see
   │        to every live core               │   the GIC page for why
   │                                        │  one can't be delivered here)
   │                                        │  _irq_handler special-cases
   │                                        │  this IPI → diverts to
   │                                        │  _companion_core_park$
   │                                        │  (dedicated 2 KB park stack)
   │                                        ▼
   │                              back in the mailbox park loop,
   │                              ready for the next companion_core_start()

The harder problem here wasn't releasing a core — it was recovering one. A DFU-triggered software reboot only resets core 0, so a companion core that had already been released just keeps running its old entry function straight through the "reboot" — it's never sitting in the mailbox park loop again, and the only recovery used to be a physical power cycle. The fix uses the one mechanism that can redirect a core that's actively running, without a hardware reset: companion_core_reset_active() sends every live core an ARM Local mailbox 0 IPI, and the assembly _irq_handler special-cases it to divert straight into a dedicated park routine instead of returning to whatever the core was doing. That routine originally reused the abandoned task's own stack, which produced crashes where TASK_WATERMARK filler bytes started showing up as return addresses — the park code ran far enough into a stack's watermarked tail that it began popping watermark bytes as if they were saved registers. It now runs on a dedicated 2 KB per-core park stack instead.

Being direct about status, since this is asymmetric multicore work and not everything here has been proven on a board: the release-and-reparking mechanism above, and the independent per-core scheduler instances it launches into, are implemented in the current source. But the project's own multicore plan docs still mark the very first milestone — confirming secondaries actually reach _start rather than being held by the boot stub — as build-verified only, not yet validated on hardware.
